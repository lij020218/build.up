## Part 1: 현재 기능 전수 점검

### 진입 플로우 (3가지 경로)

```
[앱 진입]
   ├── 역할 선택 (사장/직원/매니저)
   │
   ├─① 직접 로드맵 (수동) ─── 단계별 진행
   ├─② AI 자동 로드맵 ─────── 4단계 위저드 → AI 생성
   └─③ 이미 운영 중 ────────── 6단계 온보딩 → 운영 대시보드
```

#### 경로 ① 직접 로드맵 (수동)
| 현재 상태 | 문제점 | 설계 개선 |
|----------|--------|----------|
| 업종 선택 → 단계별 수동 진행 | 초기 진입 후 "뭘 해야 하지?" 막막함 | 각 단계 시작 시 **30초 브리핑** 표시: "이 단계에서 할 일 3가지, 예상 소요 시간, 왜 중요한지" |
| 단계 완료 조건 불명확 | 사용자가 언제 다음으로 넘어갈 수 있는지 모름 | **완료 체크리스트** 명시: 필수 항목 N개 중 M개 완료 시 자동 잠금 해제 |
| 단계 간 연결성 약함 | 이전 단계 결정이 다음 단계에 영향 안 줌 | **결정 전파(Decision Propagation)**: 업종→비용 기본값, 지역→임대료 범위, 프랜차이즈→초기투자 자동 반영 |

#### 경로 ② AI 자동 로드맵
| 현재 상태 | 문제점 | 설계 개선 |
|----------|--------|----------|
| 4단계: 아이디어→예산→지역→상호 | AI가 잘못된 카테고리로 파싱 시 "음식점"으로 silent fallback | **절대 silent fallback 금지**. AI 파싱 실패 시 사용자에게 "업종을 직접 선택해주세요" 확인 UI 표시 |
| AI 생성 중 8단계 프로그레스 | 실제 AI 호출은 1회, 나머지는 가짜 프로그레스 | 정직하게 표현: "AI가 분석 중입니다" + 실제 소요 시간 표시 (보통 5-10초) |
| 생성 결과 리뷰 화면 | 수정 불가. 마음에 안 들면 처음부터 다시 | **부분 수정 허용**: 예산/지역/업종을 개별적으로 수정 후 해당 부분만 재생성 |
| 생성된 로드맵의 정확성 | 검증 없이 바로 적용 | **Sanity Check 레이어**: AI 결과를 business-context.ts 규칙으로 교차 검증. 비현실적 수치(월매출 > 업종 상위 10% 등) 경고 표시 |

#### 경로 ③ 기존 사업자 온보딩
| 현재 상태 | 문제점 | 설계 개선 |
|----------|--------|----------|
| 6단계: 업종→가게정보→세무→월비용→유통→완료 | 6단계가 순차적이라 이탈률 높을 수 있음 | **필수 3단계(업종/가게/비용) + 선택 3단계(세무/유통/완료)** 구조로 변경. 최소 정보로 빠르게 대시보드 진입 |
| 월비용 입력이 수동 | 정확한 수치를 모르는 사장님이 많음 | **업종별 평균값 프리필**: "카페 평균 재료비 30%, 인건비 25%입니다. 맞으면 넘어가세요" |
| 온보딩 완료 후 바로 운영 대시보드 | 빈 대시보드가 보임 (데이터 없음) | **첫날 가이드**: "오늘 매출을 입력하면 내일부터 AI 코치가 분석을 시작합니다" |

### 7개 서피스 전수 점검

#### Surface 1: HOME (홈)
```
현재 구조:
┌─────────────────────────────┐
│  Welcome Hero               │
│  Progress Summary           │
│  Founder Snapshot           │
│  Stage Rail (현재+다음)      │
│  [운영중이면] Dashboard      │
└─────────────────────────────┘
```

| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| Welcome Hero | 정적 메시지 | 재방문 시에도 같은 화면 | **상태 인식형 Hero**: 첫 방문 = "환영합니다", 진행 중 = "N단계 진행 중, 다음 할 일", 운영 중 = "오늘의 매출 요약" |
| Progress | 퍼센트 표시 | 의미 없는 숫자 | **다음 마일스톤까지 남은 것** 중심: "사업자등록까지 2단계 남았어요" |
| Stage Rail | 현재+다음 미리보기 | 전체 여정 감이 안 옴 | **미니맵**: 전체 단계 도트 + 현재 위치 하이라이트 (지하철 노선도 스타일) |
| 운영 대시보드 | 별도 컴포넌트 | 홈과 대시보드의 역할 중복 | 홈 = **"오늘 한눈에"** (요약), Analytics = **"깊이 들여다보기"** (상세). 역할 명확 분리 |

#### Surface 2: CURRENT (현재 단계)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 단계 폼 | 단계마다 다른 폼 | 일관성 부족, 뭘 해야 하는지 불명확 | **통일 레이아웃**: 상단 = 단계 브리핑(왜/뭘/어떻게), 중단 = 액션 카드, 하단 = 지식/분석 도구 |
| 결정 저장 | decisions 맵에 저장 | 이전 결정을 다시 보기 어려움 | **결정 요약 사이드바**: "지금까지의 선택" 한눈에 보기 |
| AI 분석 도구 | 계약서/재무/상권 등 | 어디서 접근하는지 불명확 | **상황별 자동 추천**: 프랜차이즈 단계에서는 계약서 분석 자동 노출, 입지 단계에서는 상권 분석 자동 노출 |

#### Surface 3: ROADMAP (로드맵 타임라인)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 타임라인 표시 | 세로 리스트 | 업종/유형별 필터링 후 빈 단계가 보일 수 있음 | **필터링 후 빈 단계 숨기기** + 총 N단계 중 M단계 표시 명시 |
| 단계 상태 | current/completed/locked | locked 단계는 내용을 볼 수 없음 | **locked이어도 미리보기 허용**: "이 단계에서 할 일" 요약은 보여주되 액션은 잠금 |
| 예상 일정 | 16주 고정 | 업종/상황별로 다름 | **동적 예상 일정**: 업종별 평균 + 사용자 진행 속도 반영. "현재 속도로 N주 후 완료 예상" |

#### Surface 4: GUIDES (지식베이스)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 가이드 분류 | 인허가/세금/대출 | 업종별 필터 없음 | **내 업종 우선**: 선택한 업종과 관련된 가이드를 상단에 자동 정렬 |
| AI Q&A | 가이드 컨텍스트 기반 질문 | 환각 위험 | **소스 명시 강제**: 모든 AI 답변에 "출처: [가이드명], 최종확인: [날짜]" 표시. confidence가 "check_needed"이면 **경고 배너** |
| 정보 신선도 | freshness 메타데이터 존재 | UI에 노출 안 됨 | **신선도 뱃지**: 🟢 최신(3개월 이내) / 🟡 확인 필요(3-6개월) / 🔴 오래됨(6개월+). stale 정보는 자동 dimming |

#### Surface 5: FRANCHISE (프랜차이즈)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 브랜드 리스트 | 100+ 브랜드 | 정보 과부하 | **내 예산 필터 자동 적용**: 선택한 자본금으로 가능한 브랜드만 기본 표시 |
| 비용 데이터 | 일부 costVerified | 미검증 데이터와 검증 데이터 구분 없음 | **검증 뱃지**: ✅ 공정위 확인 / ⚠️ 추정치 명확 표시 |
| 비교 기능 | 없음 | 브랜드 간 비교 불가 | **나란히 비교 (최대 3개)**: 초기투자/월수익/폐점률/로열티 비교 테이블 |
| 폐점률 | 숫자만 표시 | 맥락 없는 숫자 | **업계 평균 대비 표시**: "폐점률 3.2% (업계 평균 8.5% 대비 우수)" |

#### Surface 6: PROFILE (프로필)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 입력 필드 | 10개+ 필드 | 한 번에 너무 많은 정보 요구 | **점진적 프로필**: 핵심 3개(업종/유형/예산)만 필수, 나머지는 관련 단계에서 자연스럽게 수집 |
| 프로필 변경 | 언제든 수정 가능 | 변경 시 로드맵/재무 시뮬 결과와 불일치 | **변경 영향 미리보기**: "업종을 변경하면 로드맵이 재구성됩니다. 계속하시겠습니까?" |
| 인증 | Supabase Auth 필수 | 익명 사용자는 프로필 저장 불가 | **익명 → 회원 전환 시 데이터 마이그레이션** 보장. localStorage → Supabase 자동 동기화 |

#### Surface 7: ANALYTICS (운영 대시보드)
| 항목 | 현재 | 문제 | 개선 설계 |
|------|------|------|----------|
| 매출 입력 | 수동 (일별 매출/고객수) | 매일 입력하는 게 번거로움 | **최소 입력**: "오늘 매출"만 입력하면 나머지는 AI가 추론. 상세 입력은 선택 |
| P&L 대시보드 | MonthlyPnL 계산 | 비용 입력이 안 되면 의미 없음 | **비용 미입력 시 업종 평균으로 가(假)계산** + "실제 비용을 입력하면 더 정확해집니다" 유도 |
| AI 코치 | todayActions + crisisActions | 매번 API 호출 필요 | **캐싱 전략**: 같은 날 같은 데이터면 캐시된 결과 표시. 데이터 변경 시에만 재호출 |
| 건강 점수 | 0-100 | 점수만으로는 행동 불가 | **점수 + 가장 큰 개선 포인트 1개**: "건강 점수 72점. 재료비율을 35%→30%로 줄이면 82점으로 올라갑니다" |
| 재고 관리 | InventoryMode별 다른 UI | 복잡함 | **업종별 자동 UI 전환** 이미 있음. 다만 빈 상태 UI 개선 필요: "첫 재고를 등록하세요" |
| 직원 관리 | 이름/시급/주간시간/보험 | 4대보험 계산 로직 | **채용비용 계산기와 연동**: 직원 추가 시 자동으로 예상 월 인건비 표시 |
| 배달 플랫폼 | 수수료/광고비 | 배달 매출 비중 분석 없음 | **배달 의존도 경고**: 배달 매출 > 50%이면 "배달 의존도가 높습니다. 오프라인 매출 비중을 늘려보세요" |

## Part 2: 12개 업종별 품질 점검 매트릭스

### 업종별 기능 동작 보장 체크리스트

모든 업종에서 다음 16개 기능이 **오류 없이** 동작해야 함:

| # | 기능 | 검증 기준 |
|---|------|----------|
| 1 | 업종 선택 → 하위 업종 표시 | 해당 카테고리의 subIndustry 목록이 빠짐없이 표시 |
| 2 | InventoryMode 자동 전환 | separate/unified/service/minimal 중 맞는 모드 적용 |
| 3 | CustomerMode 자동 전환 | membership/appointment/repeat/pipeline/ecommerce 중 맞는 모드 적용 |
| 4 | ExpenseMode 자동 전환 | 비용 필드 레이블이 업종에 맞게 변경 (재료비→원재료비→매입비 등) |
| 5 | 재무 시뮬레이션 | 업종별 벤치마크 데이터 로드 + BEP 계산 정상 |
| 6 | 상권 추천 | 해당 업종에 맞는 상권 스코어링 (categoryFit 반영) |
| 7 | 프랜차이즈 필터 | 해당 카테고리 브랜드만 표시 |
| 8 | 인허가 체크리스트 | 업종별 필수/조건부/권장 인허가 정확 |
| 9 | AI 로드맵 생성 | 업종 파싱 정확 + fallback 시 사용자 확인 |
| 10 | AI 사업계획서 | 업종 특화 내용 반영 (원가율/회전율 등) |
| 11 | AI 건강 진단 | 업종별 건강 기준 차등 적용 (F&B prime cost ≤ 60%, IT SaaS 다름) |
| 12 | AI 코치 액션 | 업종별 맥락 반영 (계절성/배달 의존도 등) |
| 13 | 로드맵 단계 필터링 | online-only/offline-only/franchise-only 정확 필터 |
| 14 | 성공 사례 매칭 | applicableTo에 해당 업종 포함된 케이스만 표시 |
| 15 | 가이드 Q&A | 업종 컨텍스트가 프롬프트에 주입됨 |
| 16 | 비용 필드 기본값 | 업종별 평균 비용 비율 프리필 |

### 업종별 특수 요구사항

| 업종 | 특수 요구사항 | 현재 상태 | 조치 |
|------|-------------|----------|------|
| **food** (외식업) | 위생허가, 원산지표시, 배달 의존도 분석 | 가장 완성도 높음 | 기준 모델로 사용 |
| **cafe-dessert** | 로스팅/베이킹 장비비, 테이크아웃 비중 | 대부분 food와 공유 | 장비 초기투자 벤치마크 확인 |
| **retail** (소매) | 재고 회전율, 시즌 상품 관리, 온라인몰 연동 | unified 모드 | 재고 회전율 메트릭 추가 필요 |
| **beauty** | 예약 관리, 시술 메뉴, 재료 소진율 | service 모드 | 예약 기반 매출 예측 로직 확인 |
| **fitness** | 회원권 모델, 시설 감가상각, 계절 변동 | membership+minimal | 회원 이탈률 메트릭 확인 |
| **education** | 수강생 관리, 과정별 수익, 강사비 | membership+content | 수강 완료율 메트릭 확인 |
| **pet** | 예약+재고 혼합, 보험/배상 | appointment+supply | 보험 관련 인허가 확인 |
| **living-service** | 출장 서비스, 소모품 관리, 단골 관리 | repeat+general | 출장 비용 계산 로직 확인 |
| **space** | 시간대별 요금, 시설 유지비, 예약률 | membership+facility | 가동률 기반 매출 예측 확인 |
| **online-digital** | CAC/LTV, 구독 모델, 서버 비용 | ecommerce+purchase | 오프라인 단계 필터링 정확성 확인 |
| **startup-tech** | MRR/ARR, 번레이트, 투자 라운드 | pipeline+infra | 스타트업 전용 재무 지표 확인 |

## Part 3: 데이터 정확성 프레임워크

### 원칙: "잘못된 정보보다 정보 없음이 낫다"

```

## Part 4: 기술 안정성 설계

### 1. API 스키마 검증 (Zod)

```
모든 API 라우트에 적용:
  Request  → zod.parse() → 실패 시 400 + 구체적 에러 메시지
  Response → zod.parse() → 실패 시 500 + 로깅 + 안전한 fallback
  외부 API → zod.safeParse() → 실패 시 graceful degradation
```

**우선 적용 대상** (AI 라우트 11개):
1. `/api/ai/roadmap/generate` — 가장 복잡, 파싱 실패 위험 최대
2. `/api/ai/dashboard/actions` — 매일 호출, 안정성 필수
3. `/api/ai/health/diagnose` — 건강 점수 기반 의사결정
4. `/api/ai/business-plan/generate` — 사업계획서 정확성
5. `/api/ai/contract/analyze` — 계약서 분석 정확성
6. 나머지 6개 AI 라우트

**외부 API 어댑터** (8개): 공공 API 응답이 예상과 다를 때 앱이 죽지 않도록 safeParse + fallback

### 2. Rate Limiting (Redis/Upstash)

```
현재: 인메모리 Map (서버 재시작 시 초기화)
목표: Upstash Redis (서버리스 호환, 영속성)

요금 방어:
  AI 라우트: 사용자당 5회/분, 50회/시간, 200회/일
  데이터 라우트: 사용자당 20회/분
  비인증 사용자: AI 라우트 접근 차단
```

### 3. Error Boundary 전략

```
레벨 1: App Root Error Boundary
  → "문제가 발생했습니다. 새로고침하거나 홈으로 돌아가세요"

레벨 2: Surface별 Error Boundary
  → Analytics 에러가 Roadmap까지 죽이지 않음
  → 해당 Surface만 fallback UI 표시

레벨 3: AI 카드별 Error Boundary
  → AI 코치 실패해도 매출 입력/조회는 정상 작동
  → "AI 분석을 불러오지 못했습니다. 잠시 후 다시 시도하세요"
```

### 4. React Strict Mode 활성화 계획

```
Step 1: next.config.ts에서 reactStrictMode: true
Step 2: 개발 환경에서 double-render 관련 버그 전수 수정
Step 3: useEffect 의존성 배열 전체 점검
Step 4: localStorage 읽기/쓰기 race condition 수정
```

### 5. 상태 관리 리팩토링

```
현재: starter-stage-demo.tsx (11,866줄) + useState 13개 + DashboardContext

목표 아키텍처:
┌─────────────────────────────────────────┐
│  Zustand Stores (도메인별 분리)           │
│  ├── useProfileStore (업종/유형/예산)     │

├─────────────────────────────────────────┤
│  Persistence Layer                       │
