## 1. 제품 경쟁력 — "진짜 차별점이 있는가?"

### 3개 모델 공통 의견
- **올인원 통합성**은 확실한 차별점. 로드맵+재무+상권+정부지원+사업계획서를 한 곳에 모은 서비스는 현재 한국에 없음
- 공공기관 시스템(K-Startup 등)의 끔찍한 UX를 파고든 포지셔닝은 영리함

### 의견 차이
| 모델 | 평가 |
|------|------|
| **Claude** | 통합성 자체가 킬러 기능. 다만 각 기능의 깊이가 부족하면 "뭐든 있지만 아무것도 깊지 않은" 서비스가 될 위험 |
| **GPT** | 네이버 스마트플레이스, 창업지원센터가 이미 상권+지원사업 매칭 제공. 통합성 외에 킬러 기능 부족 |
| **Gemini** | **"뷔페의 저주"** — 12개 업종을 모두 커버하려다 아무것도 못하게 될 위험. 1~2개 업종에 집중해야 함 |

### 의회 결론
> **12개 업종 전부를 커버하려는 욕심을 내려놓고, "카페/외식업 + 정부지원 매칭 + AI 사업계획서"로 핵심을 좁혀 압도적 품질을 만들어야 한다.** 넓게 펼치는 것은 그 이후.

## 2. 기술 품질 — "프로덕션 배포 가능한가?"

### 3개 모델 만장일치
**"현재 상태로 프로덕션 배포 불가. PoC/해커톤 프로토타입 수준."**

### 위험한 기술 부채 순위 (3개 모델 종합)

| 순위 | 기술 부채 | 위험도 | 언급 모델 |
|------|----------|--------|----------|
| 1 | **테스트 코드 0개** | CRITICAL | 전원 |
| 2 | **API 스키마 검증 없음 (Zod 미사용)** | CRITICAL | 전원 |
| 3 | **인메모리 Rate Limiting** | CRITICAL | 전원 |
| 4 | **2000줄 거대 컴포넌트 + useState 13개** | HIGH | 전원 |
| 5 | **AI 모델 하드코딩** | HIGH | Claude, GPT |
| 6 | **React Strict Mode 비활성화** | HIGH | Gemini, GPT |
| 7 | **에러 바운더리 미흡** | HIGH | 전원 |

### Gemini의 핵심 지적 (고유)
> "한국 공공기관 API는 말도 없이 응답 스키마를 바꾸거나, 에러 시 200 OK에 HTML을 내려보내는 등 기상천외한 동작을 한다. Zod 없이 방어적 파싱만 했다면 런타임에서 무조건 터진다."

### 의회 결론
> **TS Strict 100%, 모노레포, API 레이어 분리 등 기본 골격은 우수하나, 그 위에 올라간 살(테스트, 검증, 에러 처리)이 거의 없다. 뼈대만 좋은 건물에 벽과 지붕이 없는 상태.**

## 3. UX / 리텐션 — "매일 열어볼 이유가 있는가?"

### 3개 모델 만장일치
**"매일 열어볼 이유는 없다."**

### 핵심 논점

| 모델 | 관점 |
|------|------|
| **Claude** | 창업 준비 기간(2~4개월)에는 집중 사용하지만, 오픈 후에는 POS/매출관리 앱으로 이동 |
| **GPT** | 일일 체크리스트, 미션, 커뮤니티 같은 '습관성' 요소가 없어 운영 단계 이탈률 높음 |
| **Gemini** | **DAU/MAU를 지표로 삼지 말 것.** "사업계획서 완성률", "지원사업 실제 지원 횟수", "로드맵 태스크 달성률" 같은 Task Completion 지표가 맞음 |

### 의회 결론
> **build.up은 "매일 쓰는 앱"이 아니라 "창업 준비 기간의 집중 유틸리티"로 포지셔닝해야 한다.** 억지로 데일리 리텐션을 만들지 말고, Task Completion(작업 완수율)을 핵심 지표로 설정할 것. 창업 후에는 캐시노트 등으로 자연스럽게 넘어가는 것을 인정하고, 준비 기간의 밀도를 극대화하는 전략이 맞다.

## 4. 스케일링 — "사용자 1만 명일 때 버틸 수 있는가?"

### 3개 모델 종합

| 구간 | DB (Supabase) | API/백엔드 | 프론트엔드 |
|------|--------------|-----------|-----------|
| 1,000명 | OK | 인메모리 Rate Limit 위험 | 342KB 정적 데이터 로딩 지연 |
| 10,000명 | 인덱스 필요 | **AI 과금 폭탄 + 공공API Quota 고갈** | 리렌더링 지옥 (저사양 기기 프리징) |

### Gemini의 고유 지적
> "공공데이터 API(카카오맵, 상권 등)는 일일 호출 제한이 빡빡하다. 1,000명이 동시에 상권 분석을 돌리면 외부 API Quota가 고갈되어 서비스 전체가 뻗는다."

### 의회 결론
> **DB는 버티지만 외부 API Quota와 AI 과금이 먼저 죽인다.** Redis 캐싱 + AI 호출 Throttling + 공공API 응답 캐싱 전략이 스케일링의 핵심.
