# 코드 작성 전 항상 현재 코드 상태 먼저 파악

**사용자의 명시적 지시 (2026-04-17)**:
> "어떤 것을 작업하기 전에는 항상 현재 코드 상태를 파악하고 진행해. 그래야 자연스러운 기능과 ui/ux를 만들어낼 수 있어."

코드 변경이나 신규 기능 요청이 들어오면 **구현 전에 반드시** 아래 5가지를 먼저 확인한다:

## 1. 관련 기존 파일 지도 만들기
- 같은 도메인의 파일들 (components, stores, services, API routes)
- Glob/Grep으로 전방위 검색
- 이미 비슷한 기능이 있는지, 있다면 어떻게 구현됐는지

## 2. 지켜야 할 패턴 식별
- 네이밍 컨벤션 (파일·함수·타입)
- 스타일 토큰 (색상·간격·타이포)
- 컴포넌트 쉘 구조 (Hero card, Modal sheet 패턴 등)
- Props 구조와 Context 사용 방식

## 3. 데이터 흐름 추적
- 데이터 출처 (어느 스토어/API?)
- 쓰기 경로 (누가 이 데이터를 업데이트하는가?)
- 관련 스토어 간의 읽기/쓰기 의존성
- localStorage persist 여부

## 4. UX 위치 결정
- 대시보드/페이지에서 어디에 배치할지
- 시각적 이웃은 무엇인지
- 섹션 순서 맥락 (왜 이 위치여야 하는가?)
- 접기/펼치기, 스크롤 위치

## 5. 충돌 가능성 체크
- 이미 비슷한 기능이 있는가?
- 중복·경합하는가?
- 기존 기능과 통합할 수 있는가?

## 실천 방법

구현 작업 시작 시:
1. 사용자 요청을 정확히 파악
2. Glob·Grep·Read로 관련 영역 매핑
3. 큰 작업이면 Explore 에이전트를 **병렬로** 투입
4. 짧은 계획 작성 — 실제 파일 경로, 기존 패턴, 명시적 배치 결정 포함
5. 그 후 구현 착수

## 예외

다음 경우는 탐색 단계 생략 가능:
- 이미 방금 읽은 파일의 한 줄 수정
- 명백한 오타·컴파일 에러 수정
- 사용자가 직접 파일 경로 + 변경 내용을 구체적으로 지정한 경우

## 왜 이 규율이 중요한가

- **기능이 자연스럽게 느껴짐**: 기존 패턴을 지키면 학습 비용 없음
- **UI/UX 일관성**: 여기저기 다른 스타일의 파편이 아닌 통합된 경험
- **중복 방지**: 비슷한 기능을 또 만드는 낭비 제거
- **유지보수 용이**: 미래의 자신이 읽을 수 있는 코드
- **자신감 있는 구현**: 무엇이 이미 있고, 무엇을 만들어야 하는지 명확

## 체크리스트 (구현 착수 전 자문)

- [ ] 관련 파일 최소 3-5개 읽었는가?
- [ ] 기존 유사 기능이 있는지 Grep으로 검증했는가?
- [ ] 어느 스토어/API를 읽고 쓸지 명시적으로 정했는가?
- [ ] UI 배치 위치가 기존 섹션 순서와 일관성 있는가?
- [ ] 재사용할 컴포넌트 쉘·스타일이 확인됐는가?

5개 모두 ✅ 전에는 코드 작성 금지.
